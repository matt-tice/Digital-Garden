Summary

Functional language

Haskell doesn't have variables in the sense of an imperative language All "variables" are really explicit values that we give a name

  • you aren't allowed to actually vary the value; every "variable" is a constant

This is actually fantastic for optimization

  • compilers can optimize around the fact that all variables are constant
  • for ex. you can replace all occurances of a certain variable name by a pointer to a single shared memory layout
    • ordinarily, if you did that for a non-constant variable, you'd risk the memory address being overwritten with different values as you change the scope

Folds

Basically these things take a list and replace all of the cons operators (:) with a specified function f, and replace the empty list [ ], with a base-case z

  1. foldr

    Processes a list from right to left

    • it computes f1(f2(f3(z)))
    (a -> b -> b) -> b -> [a] -> b

    The first object is f

    • we think of it as a list of functions, indexed by elements in our list

    The second is z The third is your list

    Basically f z [1,2,3] becomes f1(f2(f3(z)))

    So basically, it allows you to evaluate a composition of functions fi :: b → b on a fixed element z

    Note: foldr is computed lazily

    • if it can return without having to compute the nested compositions, it will

  2. foldl / foldl'

    Processes a list from left to right

    • basically it wraps composition in the opposite way
    (b -> a -> b) -> b -> [a] -> b

    The first object is g

    • we think of it again as a list of functions gi = g(-,i) : b → b

    The second element is the base case The third is the list

    We get g(g(g(z,1),2),3) = g3(g2(g1(z)))

    Note: Haskell's laziness treats this a little weird

    • it will skip over g1(z), leaving it unevaluated (we call this a thunk)
    • then it'll do the same at g2, and so on, until it gets to the end
    • only then will it try to evaluate the whole thing
    • because of this, you can actually run out of memory, since it'll leaving these thunks behind

    Note: foldl' is usually better, because it evaluates at each step, instead of combining a bunch of unexecuted lazy expressions

Compiler

We can alter its behaviour using a language pragma: {-# LANGUAGE [option] #-}

This tells GHC to treat strings as arrays of bytes, as opposed to inefficient linked lists of characters.

Sum Types

data sumTypeName
  = constructor1 Type1
  | constructor2 Type2
  deriving (Show, Eq)

Constructors are functions that instantiate values. The Type next to them is what you have to pass into the function

What's happening under the hood, is that we get a function

constructor1 :: Type1 -> sumTypeName

Sum types say that the data type can be instantiated by any of the listed constructors.

deriving(Show, Eq): these are properties we give our defined type

  • Show allows us to print it to the terminal
  • Eq allows us to use == on it

Product Types

  } deriving (Show, Eq)

This says that the data constructor is also prodTypeName

  • this tells us there's only one valid way to construct the data form

The info inside of the curly brackets are records: they tell us what information our data type must contain (it has to contain all of them)

newtype

newtype doesn't have any runtime cost, unlike data

newtype SemanticID = SemanticID Word64

In this snippet, two things are happening:

  1. We're defining a new type called SemanticID
  2. We're also defining a data constructor named SemanticID

The point is that now that SemanticID is created from a 64-bit integer, but it isn't itself considered a 64-bit integer by the program

  • this is a form of type safety
  • it says that we can't just pass any random 64-bit integer into a function expecting a SemanticID; we have to explicitly say that our integer is of type SemanticID
  • very cool!

Characters

All characters are boxed

  • they're their own independent objects living in some random place on the heap

They're made up of

  • header (8 bytes)
  • unicode point data (4 bytes (32-bit unicode), padded to 8)

Lists

Lists are denoted with square brackets, like [1,2,3], but their actual structure under-the-hood is nested constructors:

1 : (2 : (3 : []))

The colon : is called a node or a cons operator. It's actually a function with shape

(:) :: a -> [a] -> [a]

It takes an element of type a and a list of type [a] and returns a list of type [a] :: defines a type

A node contains two pointers:

  1. to the associated character
  2. to the next node (or to [ ])
myList = 1 : 2 : 3 : []

-- is the same as
1 : (2 : (3 : []))
-- because : is defined to work from right to left


(:) :: a -> [a] -> [a]

Disadvantages

Lists are stored non-contiguously

  • so you constantly get cache misses

Because lists are generated lazily, if you need to go through an entire list, it's inefficient

A single character usually takes 1-2 bytes in another language. In a haskell list, on average, a character takes up to 24 bytes because it's really made up of

  • a node
  • two pointers
  • a boxed character header

Advantages

Lists are generated lazily

  • so you can actually manipulate lists that are larger than your RAM
  • you just create the list as you go
  • and as you finish a step and move on to the next one, the GC reclaims the node

You can prepend data in O(1)

  • you just point into the beginning of your list

Strings

In basic haskell, String is an alias for a list of characters:

type String = [Char]

Consequently, it's a long chain of nodes:

h : e : l : l : o : []

Since each character is blocked, they're all scattered around the heap, which makes them slow to read

Treats strings as contiguous byte arrays encoded in UTF-16

Because it's contiguous, you don't need pointers, since you know that the next character is just in the next part of the cache line

  • characters take up 2 bytes

Scans the text block for every occurance of a fixed string and breaks it into a list at those points.

  • instead of creating a list made up of the strings of text you get, it just creates a list of pointers to the memory address and offset of each of the chunks in the list

Text → Text

  • just changes the length and offset to start after the whitespace and end right before

Makes all of the letters lowercase

words

Text  → [Text]

Splits text into a list of words

It's actually smarter than splitOn, which doesn't know how to handle double-spaces or other kinds of white spaces, like tabs, newlines, and carriage returns.

Monads

  • there's no native concept of time or sequence in Haskell

Monads force things to evaluate in sequence

When would you use this?

When interacting with hardware states

  • you can't read a memory address before you allocate it

Optimizing

Streaming-Mutation

When you mutate a string, you never want to store the whole string and then mutate it, because you'll get a string scattered throughout the heap

Instead, you modify in place, one letter at a time

  • you keep your string in the L1/L2 cache

Scoping

let … in

let can be used anywhere in your code that a value is expected

  • it defines local variables

in defines the expression where the local variables are valid

calculateArea :: Double -> Double
calculateArea radius = 
    let piVal = 3.14159
        r2    = radius * radius
    in piVal * r2

let ... in is used typically inside of lambda functions or if-thens, where where can't be used

where

It's very similar to let, but you have to use it inside of a function

  • the nice thing is that where automatically knows about every argument in the function it's attached to
calculateArea :: Double -> Double
calculateArea radius = piVal * r2
  where piVal = 3.14159
        r2    = radius * radius

It can also work across sum-types:

describeNumber :: Int -> String
describeNumber n
    | n > 0     = "Positive: " ++ show n
    | n < 0     = "Negative: " ++ show n
    | otherwise = "Zero"
    where nSquared = n * n -- This nSquared is available to ALL guards (|)

Pattern Matching

case … of

case takes a value and compares it against a series of patterns, to decide what to return

case expression of
    pattern1 -> result1
    pattern2 -> result2
    _        -> defaultResult

functions in haskell are computed using case...of, under the hood

factorial :: Int -> Int
factorial x = case x of
    0 -> 1
    n -> n * factorial (n - 1)

case ... of and if ... then are computed in the exact same way

  • so they're equally performant

but case is often clearer, and allows you to handle more cases, without having to nest a bunch of if statements.
