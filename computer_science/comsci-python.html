AKA execution stack / interpreter stack

This is a stack of stack frames

  • once a function returns, its stack frame is popped from the call stack

Namespaces / Scopes

Namespaces are maps

  • Names → Objects
  • usually implemented by dictionaries

Scopes of namespaces are the actual regions of text in a python program where that namespace is accessible

  • in a scope of a namespace, referencing a name will use the namespace to find the corresponding object

Functions create local namespaces when called, and those NS are forgotten when the function returns or raises an exception that isn't handled in the function

  • in other words, when you call a function, the local NS has a new map added to it, which is a name of the function referring to the corresponding function object
  • then when the function returns, the mapping in the NS is deleted

Similarly del x is really forgetting the map from x to its object in the local NS

Scope Hierarchy

Scopes are checked in the following order

  1. The local names of a function
  2. The scope of enclosing functions (wrappers)
    • these are non-local and also non-global
  3. The current module's global names
  4. The built-in names

Assignments to names always go to the local scope, unless you use a global or nonlocal keyword

import and def find the names of the modules/functions in the local scope

Helpful Example

def scope_test():
    def do_local():
        spam = "local spam"

    def do_nonlocal():
        nonlocal spam
        spam = "nonlocal spam"

    def do_global():
        global spam
        spam = "global spam"

    spam = "test spam"
    do_local()
    print("After local assignment:", spam)
    do_nonlocal()
    print("After nonlocal assignment:", spam)
    do_global()
    print("After global assignment:", spam)

scope_test()
print("In global scope:", spam)

Will print

After local assignment: test spam
After nonlocal assignment: nonlocal spam
After global assignment: nonlocal spam
In global scope: global spam

Here's what's happening under the hood:

  • do_local defines a map from the name spam to the str object "local spam"
  • do_nonlocal first creates a nonlocal name called spam, and then defines a map from this nonlocal-spam to the str object "nonlocal spam"
  • similarly, in the global case
  • now, in scope_test the assignment spam = "test spam" is assigning non-local spam to the object "test spam" (which is really local in the eyes of scope_test, but it's the same name in the scope_test NS that do_nonlocal was referring to)
  • and the print function in scope_test is referring to that non-local spam
  • outside of the functions, in the final print, we're referring to the global spam, which was set by do_global

Arrays

DYNAMIC ARRAYS: In Python,

LISTS: Ordered. Mutable.

  • Square brackets (this is called creating a literal)
  • Insert elements with .append() and .insert(). Similarly, you have .pop() and .remove()
  • In python, .remove() and .insert() actually work by first shuffling the elements around, and then modify the stuff at the end (final element) of the list, and then shuffle back into the right order

As a consequence, if you want to work with an element at the very beginning of the list, it will actually take a lot of time

LINKED LISTS: Ordered. Their time complexity and the way they store data is different from ordinary lists.

  • Elements are called 'nodes' The first node is the 'head' Each node has 2 pieces of data: the value of the node, and a reference to the next node in the list

  • Useful for stacks and graphs (like actual discrete graphs from math)

  • The beginning of a linked list has O(1) time complexity (you always know where the first node is) The end of the list has O(n), since you have to travel from the first element to get there

  • Insertion/deletion at a specific point is also O(n) for the same reason

  • Worse at element lookup than lists, since to get to element k, you have to traverse the whole list to get there

  • Doubly linked lists have each node also pointing backwards; that lets you traverse from the end as well, reducing the time complexity

  • Circular linked lists go from the final element in the list back to the first element

In order to create a linked list

SPLICING:

If we have 2 linked lists, how do we put them together?

  • You know you can do it in at least O((n+m)log(n+m)) time Take both lists, put them into an ordinary list, sort the list, and then construct the new linked list from this sorted one.
    • constructing the n + m sized list is O(n+m)
    • sorting the n+m sized list is O(log(n+m))
    • so it's a total of O((n+m)log(n+m)) time complexity
  • space complexity is O(n+m)

How do we improve this?

  • We should build and sort at the same time:
    • At each step you take the smaller head of the two linked lists, and add it
    • This is called a recursive merge or top-down

Time is

  • O(n+m)

Space is

  • O(n+m)

There's an even better way though! It's called iterative merge or bottom-up merge

  • It basically does the same thing for time complexity, but it reduces space complexity

QUEUES: First-in/First-out (FIFO)

  • Linked lists are better
  • .popleft()

STACKS: Last-in/First-out (LIFO)

  • Linked and unlinked lists perform the same
  • For a linked list, you just add things in the reverse order: every new element becomes the new head

Exceptions

Flow

Errors during execution.

We can write programs that handle specified exceptions

try:
  x = (int(input("Please enter a number: ")))
  break
except ValueError:
  print("That wasn't a number, fool.")
else:
  ...
finally:
  ...

How it works:

  • the statements in the try block are evaluated
  • if no exception occurs, we jump to else and then finally
  • if there's an exception found in try, we jump to the corresponding except (if there is one), followed by finally

In particular, finally always evaluates

With

The with keyword allows you to write try-except-finally statements in a cleaner way

  • they rely on context managers
with Expression as Target:
   Suite

# is the same as

manager = (Expression)
enter = manager.__enter__
exit = manager.__exit__
value = enter()
hit_except = False

try:
   Target = value
   Suite
except:
   hit_except = True
   if not exit(*sys.exc_info()):
      raise
finally:
   if not hit_except:
      exit(None, None, None)

When you execute with, it will

  1. evaluate a Expression to get a context manager
  2. load the CM's __enter__ and __exit__
  3. invoke __enter__ and assigns its return value to the Target in the with statement
  4. the Suite is executed
  5. __exit__ is invoked
    • if any exception arose, it's passed along as three arguments (type, value, traceback) to __exit__

Context Managers

These are designed to work with resources that will only be used for a fixed period of time

  • after that period, the resources should be freed up

If you don't close resources, it risks using up all of your memory

Once you have a context manager defined, you can call it with the keyword with

Built-in CM

Files already have a built-in CM

with open("file.txt") as f:
    data = f.read()

We never need to call close, because it's all taken care of by the CM

Creating a CM

CMs are classes They need two methods

  • __enter__
  • __exit__

Using raise is useful, because the traceback will point to the specific moment of the code when the exception was raised

But it's also extremely useful to handle edge cases
